# Negotiation, automatic picture quality, and A/V synchronization plan

Research baseline: Halo commit `66770868639d88210519f1c14e971e0df06b0068`; Scrypted local checkout `50b8668ea8d36f281d5ab6d152cd47f3d45e57f5`; Halo's pinned HAP upstream commit `25e8bea26a64309a47184dec478479483fbdd50c`, released 2.2.3 plus existing halo.2 storage/transport extension. Exact file hashes are in `provenance.json`. This work changed only this research directory. No application, server, account, service, or device changes were made. `probe.py` invokes read-only contract/clock methods with synthetic numbers; it creates no network or media.

## Findings to communicate before implementation

1. **Advertising 1080p does not make Apple choose it.** Halo already advertises 1920×1080 at 30 fps, alongside720p and smaller modes (`camera.ts:77–79`). The selected 720p30/299 kbps request is Apple's actual stream contract, forwarded from SelectedRTP TLV by HAP. There is no preference/force-quality field in the public VideoStreamingOptions API. Advertising only 1080p or putting it first cannot guarantee better quality and can remove useful remote/watch fallbacks. Public API evidence: [advertised options](https://developers.homebridge.io/HAP-NodeJS/types/VideoStreamingOptions.html), [selected VideoInfo](https://developers.homebridge.io/HAP-NodeJS/types/VideoInfo.html), and the pinned installed `RTPStreamManagement.js:511–568` parser.
2. **299 kbps is a real constraint, not proof that Halo discarded a higher Apple request.** At30 fps it is only about 1,246 payload bytes/frame on average. A synthetic44,032-byte IDR already requires 1.178 seconds at 299 kbps before RTP/SRTP overhead;70,656 bytes needs 1.890 seconds. Halo's current full-AU deadline is1 second, so these cannot be transparently copied at that ceiling. `probe-results.json` records this arithmetic. Do not raise the negotiated rate behind Home's back.
3. **An observed37 kbps average under a299 kbps ceiling is not automatically a defect.** Maximum bitrate is a ceiling, not a requirement to add bytes to a static scene. VBR may legitimately use much less. Current packet/octet counters do not prove decoded frame cadence, missing pictures, or available network capacity, and detailed receiver reports are not retained. Measure complete access units/unique presentation timestamps, actual frame dimensions/cadence, keyframe intervals, content-independent rate windows and authenticated RR data before diagnosing underutilization. Do not add padding, raise the cap, change quality presets, or blame the network from that one average.
4. **Full resolution and encoded passthrough cannot both be promised for every request.** Current copy requires matching actual SPS profile/geometry, compatible level, progressive8-bit4:2:0, no reorder, known FPS within selected rate, plus a rolling byte budget (`h264.py:305`, `transcode.py:301,388`). Unknown source FPS does not prove incompatibility, but current code conservatively adapts. Source1080p cannot be turned into selected 720p by repacketization. A smaller source cannot yield new detail by upscaling. [FFmpeg streamcopy](https://ffmpeg.org/ffmpeg.html#Streamcopy) describes the decode-free distinction; [H264 RTP](https://www.rfc-editor.org/rfc/rfc6184) governs payload/parameter compatibility.
5. **Scrypted's permissive copy path is a comparison point, not a compliance guarantee.** Its default FFmpeg path selects `copy`; selected dimensions are sent upstream as client hints rather than hard source constraints. RECONFIGURE usually forwards bitrate to provider feedback, if available; otherwise it logs that adaptive feedback is unavailable. Halo currently applies width/height/fps/bitrate reconfiguration through its own worker. Copying Scrypted's behavior wholesale could send a stream different from Apple's selected geometry/rate. Relevant pinned local files: `camera-streaming.ts:188–189,280–350`, `camera-streaming-ffmpeg.ts:45–69`.
6. **The two timing paths need a shared correlation model, not an arbitrary audio delay.** Halo has real source-SR observation with current-source/epoch guards, but its no-SR fallback returns the same input receipt for all outputs made from that input. An actual-method scratch probe of one 60 ms source packet converted into three 20 ms outputs produces three equal presentation estimates; current SR extrapolation differs by 37.5 ms from one fixed input-source anchor, including 2.5 ms encoder lookahead. This is a proven local mapping difference, not a measured physical lip-sync error.
7. **Video reconfiguration currently preserves monotonicity but changes the RTP/time mapping.** `HomeKitLiveManager.reconfigure:634` calls `_reset_timestamp:681` in the same capture epoch. The scratch probe with a2-second source gap produces next RTP93,000 instead of affine-continuous270,000, compressing1.967 seconds of media time. Sender reports may make a receiver adjust to the changed mapping; no physical failure is asserted. It deserves an explicit reconfiguration continuity test and a stable mapping design.
8. **RR data currently proves little beyond liveness/loss requests.** Halo authenticates and bounds feedback, but `Feedback` retains PLI/NACK/BYE and a report count; per-report loss, jitter, LSR and DLSR are discarded (`rtp.py:125–175`). That prevents responsible adaptation diagnosis. [RFC3550](https://www.rfc-editor.org/rfc/rfc3550) distinguishes report statistics and RTP↔common-time correlation; an RR does not reveal Apple's rendered A/V timing.

## Implementation model proposed for owner approval

### A. Keep negotiation authoritative and make decisions explainable

Introduce one immutable internal per-view decision, without user FFmpeg arguments:

- `supported`: locally qualified codec/profile/level/resolution catalog;
- `requested`: exact Home START or RECONFIGURE fields and a local monotonically increasing configuration generation;
- `source`: current capture/config epoch and observed SPS, FPS confidence, reference ordering, rolling payload/wire rate and IDR size;
- `applied`: actual encoded output properties, copy/adapt/waiting state, and a finite reason such as geometry, profile, unknown cadence, bitrate, keyframe burst, or source reset.

Use first current SPS/PPS+IDR to decide. Copy immediately only when actual format and that complete access unit meet the contract. Continue observing the real rolling budget. Otherwise adapt once using a locally qualified internal preset, selected geometry/rate/profile/level, actual source PTS, existing reference libopus for audio, and preserved source aspect ratio. No metadata relabeling, splitting reference chains, invented frames, or forced1080p response to a720p request.

A bounded source cadence observer may later qualify VUI-absent sources from real complete access-unit timestamps across at least two GOPs, distinguishing gaps/reorder from FPS. This can eliminate avoidable encoding, but only after dedicated H264 compatibility and Apple tests. More permissive profile-subset copying is a separate optional experiment; exact-profile matching remains until RFC6184 constraint compatibility and physical receivers are proven. Do not weaken unknown-source handling speculatively.

Current HAP options expose global profiles/levels beside resolution tuples, not every per-resolution constraint. Keep only actually qualified combinations at admission, test1080p with level 4.0 and720p with 3.1+, and do not claim capability ordering forces Apple's choice. Any simplification of advertisement must be qualified with old/new iPhone, Home hub and remote clients before changing the published catalog.

### B. Automatic rate control with complete-unit pacing

Use one definition for selected bitrate versus encoded payload and wire overhead. Current worker targets the entire selected bitrate while the pacer charges protected RTP bytes, including framing and retransmissions. Measure this difference rather than assuming target bitrate guarantees queue stability. Internal rate control must leave computed framing/recovery headroom; the exact margin is selected by synthetic high-motion measurements, never an exposed FFmpeg flag. [FFmpeg rate-control documentation](https://ffmpeg.org/ffmpeg-codecs.html) distinguishes target, maximum rate and buffer size.

Retain finite full-AU admission and source-age fences. Bound encoder VBV and IDR bursts to what the transport can finish within its allowed latency. A low299 kbps request may visibly limit720p motion detail; no encoder can guarantee original high-rate detail in that budget. Prefer stable useful output over allowing an IDR to create a multi-second queue. Preserve GOP references when dropping: request/wait for a fresh actual IDR, or force a new encoder IDR. Do not drop arbitrary P-frames then call the output healthy.

Honor Home RECONFIGURE transactionally: exact scoped owner, retain SSRC/key/sequence, apply only the fields present in [ReconfiguredVideoInfo](https://developers.homebridge.io/HAP-NodeJS/types/ReconfiguredVideoInfo.html), stop old output at a bounded access-unit boundary, and acknowledge applied configuration separately from first actual new-config frame. A rejected or retired operation must retain existing cleanup/callback ownership. Configuration generations prevent an old worker result from appearing after the new contract was acknowledged. Source rate/resolution controls are currently absent from Halo's Ring capture seam; do not advertise upstream adaptive feedback until a public/pinned SDK path is proven.

### C. One media timeline shared by audio/video and sender reports

Add a small view-owned timeline coordinator, rather than two unrelated clocks. It owns current capture epoch, wrap extension, track source rates (video 90k, original Opus 48k), classic-HAP output rate (selected audio rate), one monotonic/wall-clock correlation, source-SR confidence, and one stable per-track affine output RTP mapping.

When valid matching-epoch source SRs exist, use their common NTP reference to correlate both tracks. Preserve the source-sample PTS through decode/resample/encode, including native lookahead and B-frame presentation order. A sample's presentation estimate is computed from source PTS and the frozen correlation, never from when the worker happened to return it. On the same source epoch, RECONFIGURE changes codec settings but keeps that mapping and elapsed RTP time. The arrival of a later SR must not silently jump one track's RTP origin. Validate drift/age/SSRC/rate and either promote both correlations coherently within a proved bound or keep the honest fallback until a clean epoch restart.

Without source SR, freeze an explicitly named receiver-estimate mapping from the first admitted source timestamps/receipts; advance by actual source PTS and known packet duration, not one receipt per converted output. Receipt time contains network and packetization delay, so this fallback cannot prove capture-accurate lip sync. Bound any automatic common playout alignment; never stretch the500 ms media freshness policy or replay stale syllables to create apparent sync. An initial live-edge skip does not authorize recording-history removal.

Generate outgoing SR NTP and RTP values for the same sampled instant and same fixed mapping. Keep the classic-HAP negotiated-rate audio clock separate from standard Opus 48k and Scrypted's optional modern48k mode. [RFC7587](https://www.rfc-editor.org/rfc/rfc7587) specifies the standard RTP clock; classic-HAP exception here is implementation evidence, not a general RFC rule. Pinned Scrypted's `camera-streaming-srtp-sender.ts:75–119,136–154` instead retains an RTP/send-wall-clock pair and rewrites audio time from packet count; that is simpler but does not itself prove source capture synchronization under unequal processing delays.

Review compound RTCP/SDES CNAME with the actual classic-HAP receiver contract. Halo and the compared Scrypted sender currently emit an SR alone. RFC3550 compound-RTCP rules and [RFC5506](https://www.rfc-editor.org/rfc/rfc5506) reduced-size negotiation are relevant, but this is a qualification item, not a proven cause of the current user's symptoms. If adding CNAME is required/accepted, use one opaque per-view identity across its two tracks, not a hostname/account/camera identifier.

### D. Feedback and safe observability

Preserve authenticated current-SSRC receiver reports into bounded counters/EWMAs: loss fraction/cumulative delta, jitter converted with the actual track clock, RTT only from a matching owned SR/LSR plus valid DLSR, PLI/NACK rate, and feedback age. Keep fixed windows and bounded correlation caches, no per-packet log. Do not treat report arrival as a receiver-render timestamp or infer WAN from an address alone. Distinguish source delay, worker wall/CPU time, queue wait, pacing, UDP backpressure, and receiver loss. Automatic quality reduction can use these observations within the current Home contract; raising resolution/bitrate beyond that contract requires a new controller selection.

## Proposed work packages and qualification gates

These are future implementation slices, not code changes made by this research. The root proposal groups the full repair into seven slices: metadata/RR read-side; audio recovery/bounded egress; legacy lock isolation; video cadence/GOP; pacing/reference recovery; quality/A/V/reconfigure; installed plus real pilot. The packages below map mainly to its slices1,4,5,6 and7, rather than adding a competing overall sequence. No forced1080p, fabricated profile metadata, or classic-HAP 48k wire-clock change is proposed.

| Slice | Owned change | Must pass before next slice |
|---|---|---|
| Q1 | Decision model, actual source/output metadata and finite copy/adapt reasons; strict START/RECONFIGURE cases | Public HAP TLV tests select720p30/299 while1080p is advertised; exact wire request preserved; invalid profile/level/dimensions fail with exact-owner cleanup; no secret/payload logging |
| Q2 | Internal rate/IDR budget and full-AU queue control; optional measured-cadence copy qualification | Independent SRTP receiver decodes actual output; byte-exact VCL/SPS/PPS on copy; actual SPS/profile/dimensions and measured FPS/rate on adapt; high-motion299/500/1000/2000 kbps,15/24/30 fps and IDR-burst matrix; one-hour queue/memory bound |
| Q3 | Shared timeline, stable same-epoch RECONFIGURE mapping, exact SR pairs and bounded RR stats | Synthetic synchronized flash/impulse with known source SRs; audio 20/30/40/60 ms, Opus60→20 conversion/lookahead, video 15/24/30, copy/adapt, reconfigure, RTP wrap, SR delay/loss/reorder, clock drift/step, source reset, and asymmetric worker delays |
| Q4 | Installed release plus Apple LAN/WAN/capacity qualification | All below; retain a clear rollback path and report untested combinations individually |

Q3 proposed numerical gates: with valid synthetic source SRs, SR RTP↔time arithmetic within one clock tick; decoded flash/impulse alignment within one video frame plus one audio packet, with a ceiling80 ms at 15 fps or50 ms at 30 fps; additional drift≤20 ms over30 minutes. Receiver-estimate tests must expose their uncertainty instead of claiming source-NTP accuracy. No timeline jumps, out-of-order media admission, stale output, reference-chain corruption or cross-scope output after reset/reconfigure/privacy changes. Validate real cumulative audio duration and RTP advancement, not only pitch or packet count.

Q4 physical plan (owner-run only after implementation approval):

- Establish same-camera Ring-app and current Halo baselines without simultaneous conflicting live owners; record source format and Apple selection separately. Do not save household audio/video by default. Use an owner-visible synthetic flash/clap/timing display for measurements, with explicit permission for any recording.
- LAN iPhone/iPad/Mac on good Wi-Fi; hub wired and hub Wi-Fi; cellular remote; remote Wi-Fi through Home hub; Watch/thumbnail as a separately qualified lower-quality case. Record OS/app/hub versions and which path actually carried the stream; do not assume every local request is direct.
- Cold source and shared warm source, live open/close30 cycles, mute/unmute/volume/light/siren changes during live, network transition,10-minute steady views and30-minute sync runs. Two simultaneous supported views must not trigger extra Ring owners or cross-camera interference. HKSV remains off for live qualification, then recording concurrency gets a separate explicit matrix.
- In an isolated test network only, inject bounded RTT20/80/150 ms, jitter0/20/50 ms, loss0/1/3%, rate changes and MTU128/512/1200/1228/1378. No `tc` changes on the real service host during research. Correlate selected/reconfigured rate, output rate, source-age drops, backlog, NACK recovery and decoder continuity.
- Proposed targets to agree against baseline: no false success followed by teardown, no repeating worker-reset cascade, all 30 healthy-LAN opens succeed, no unexplained packet/callback/session loss, no steadily increasing queue/RSS/FD/worker count, and no long-term A/V drift. Physical synchronization target: absolute flash/clap error≤100 ms on LAN and≤150 ms on WAN, without drift growing beyond 50 ms during15 minutes. These are project acceptance targets, not promises about an unknown upstream/network. Record P50/P95 startup and Halo-added latency; source Ring/cloud latency and Apple's rendering latency must remain distinct. Set their numeric release thresholds after the baseline measurements, not from inference alone.
- Independently decode extracted-release SRTP/media and repeat full native/Node gates. Validate actual source clock mode used, not merely capability availability. A successful localhost/fixture test is not Apple physical qualification.

## Scope boundaries and owner decisions

No backend swap is necessary to begin Q1–Q3. Retain pinned aiortc, PyAV/libx264/libopus, public HAP delegate and the existing process/privacy/cleanup architecture. A shared timeline and controlled reconfigure handoff are a contained but meaningful media-path rework and should be included explicitly in the implementation proposal. Approval is required before replacing that architecture, changing HAP to a modern/multitier/H265 protocol, adding another HAP fork, adopting hardware encoder dependencies, changing Ring's upstream transport/backend, or adding user-adjusted FFmpeg arguments. None of those is justified by current evidence.

Unknowns that must stay visible: actual per-camera H264 SPS/profile/VUI/bitrate/GOP at this user's Ring source; whether both actual source SRs are present and common-clock coherent; Apple's reason for its720p299 selection; actual Apple playout offset; which modern-clock features are publicly negotiated versus Scrypted-specific. Metadata-only observations can answer some; only controlled Apple playback can answer the rest.
